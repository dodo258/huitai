# 会话台 v0.1.3 发布前代码审计

2026-11-23。基线为 v0.1.2 的 `42a4c75`，被审版本为 `12327d22499043b96f3742caa8c3360433d049f3`。核查了两点之间的提交历史和完整差异，覆盖 72 个提交、117 个文件。共发现 27 项问题（高 1、中 19、低 7）。以下本地行号均指被审版本。

**建议发版前先修会话认错的问题。** 在同一项目仅有一个候选会话时，回车仍有可能接进另一个终端进程。另有一条独立的跨厂商错接路径。数据库方面，普通只读查询可以改动厂商目录里的 WAL 辅助文件，错误回退还会读到不完整的历史。

## 打开、托管与中断恢复

**01｜高｜新建会话认错，回车和中断恢复都可能选错对象**  
`src/ui/runtime.rs:530`、`src/ui/runtime.rs:539`、`src/ui/runtime.rs:371`、`src/sources/kimi.rs:239`。在会话台按 `n` 新开 Kimi A，保持空白。在同项目的另一个终端新开 B，发一句话后退出。A 没有用户发言，索引只列 B。匹配只要求厂商、目录、创建时间和候选数量吻合，B 通过全部条件。临时测试得到两项结果：点击真实 B 返回 A 的临时托管 ID；A 的进程异常中断后，恢复表也把真实 B 映射到 A。此时回车会切到 A，接下来输入的内容进入错误会话；按 `R` 则会把 B 当成待恢复项。建议从本次启动的进程或厂商会话接口取得真实 ID 并持久化绑定。取得凭据前，保留独立的托管项，停止按时间自动认领。

**02｜中｜两家 CLI 使用相同的显式 UUID 时，后打开的一家会接回前一家**  
`src/sources/gemini.rs:312`、`src/sources/qwen.rs:258`、`src/ui/runtime.rs:526`、`src/host/daemon.rs:751`、`src/opener/tabs.rs:83`。分别用 Gemini、Qwen 的 `--session-id` 为同一任务指定相同的合法 UUID，各聊一句后退出。列表按厂商保留两条。依次在会话台打开时，守护进程只用原始 ID 执行 `entry(spec.id).or_insert_with(...)`，标签页也只按这个 ID 聚焦。用两份不同厂商的登记实测，两次均返回成功，最后查到的仍是 Gemini。建议给托管、事件、标签页使用含厂商的内部标识；调用厂商 CLI 时再取原始 ID。两家的参数出处见文末。

**03｜中｜确已托管的新对话显示为已停，实时预览和结束操作失效**  
`src/ui/runtime.rs:574`、`src/ui/runtime.rs:913`、`src/ui/app.rs:578`、`src/ui/app.rs:729`、`src/ui/app.rs:1369`。只开一个 Hermes、Kimi 或 OpenCode 新会话，发言后保持进程运行。即使识别出了正确的临时托管 ID，界面也只留下真实 ID 的集合。这个集合只用于排除“别处在用”，状态、等待计数和快照仍用真实 ID 查临时 ID 下的事件。按 `x` 会得到“这条对话没有在后台跑”。建议让已确认的映射参与状态、预览、已读和结束操作；有歧义的候选继续单独处理。

**04｜中｜Kimi 和 OpenCode 1.x 的批量续做会误报成功**  
`src/sources/kimi.rs:104`、`src/sources/opencode.rs:315`、`src/ui/runtime.rs:1752`。对已中断的会话按 `R`。Kimi 直接丢弃 `message`；OpenCode v1.19.6 的恢复页把 `--prompt` 填入编辑框，仍需按回车。两种情况都会计入“已在 N 个新标签页接着做”。建议按实际能力分别报告“已发送”“待按回车”“需手动输入”，或使用厂商支持的交互发送接口。OpenCode 2.x 已有主动提交路径，应分版本处理。[Kimi 2.7.2 命令](https://github.com/MoonshotAI/kimi-code/blob/56145f8/docs/en/reference/kimi-command.md) · [OpenCode 1.19.6 恢复页](https://github.com/anomalyco/opencode/blob/v1.19.6/packages/tui/src/routes/session/index.tsx) · [OpenCode 2.x 恢复页](https://github.com/anomalyco/opencode/blob/ee5fe34e136488a1839ac73bcca8321c51a31b75/packages/tui/src/routes/session/index.tsx)

**05｜中｜升级期间，新厂商枚举会使旧客户端整份托管列表解码失败**  
`src/core/vendor.rs:12`、`src/host/protocol.rs:26`、`src/host/protocol.rs:152`、`src/host/daemon.rs:687`。旧会话台连到同时托管 Claude 和 Kimi 的新版守护进程，双方按协议 1 握手。用 v0.1.2 原版类型解码，只含 Claude 成功，增加一条 Kimi 即报 `unknown variant kimi`。连 Claude 的初始状态也收不到。反过来，旧守护进程有活跃对话时会保留运行，新界面向它发送新厂商的 Spawn 也失败。建议让握手协商厂商能力，为旧客户端过滤它能解码的记录，并在新客户端明确提示哪些厂商须等待旧守护进程退出。

## 数据库读取与厂商历史

**07｜中｜SQLite 只读查询会写共享内存文件，回退还可能漏掉已提交记录**  
`src/sources/sqlite.rs:20`、`src/sources/sqlite.rs:29`、`src/sources/hermes.rs:105`、`src/sources/opencode.rs:59`。用 macOS 系统 sqlite3 和脱敏 WAL 库实测：写连接开着时，读取前后主库和 WAL 内容摘要相同，`-shm` 摘要改变；可写目录只放主库和 WAL 时，读取创建了 `-shm`。另把有一条已提交、尚未 checkpoint 的记录的主库和 WAL 放到只读目录，且无 SHM；普通查询报错，适配器改用 `immutable=1` 后计数从应有的 1 变成 0。`src/index/mod.rs:489` 会把成功返回的部分视图当完整列表。建议对无法取得一致快照的情况返回可重试错误并保留缓存。若承诺厂商目录零写入，须在私有位置读取经一致性校验的快照，或采用满足该约束的读取方式。此次未观察到厂商正文被改写或持久写锁。[SQLite 关于只读 WAL 的说明](https://sqlite.org/wal.html#read_only_databases)

**08｜中｜Hermes 的单个越界时间戳可终止所有厂商的后台索引线程**  
`src/sources/hermes.rs:118`、`src/sources/hermes.rs:278`、`src/index/watch.rs:228`。损坏或导入的库里，某条消息的 REAL 时间为 `1e20`。它通过“有限且非负”的检查，在 `Duration::from_secs_f64` 处超出范围并 panic。扫描所有会话的聚合时间发生在来源过滤之前；后台扫描线程随栈展开退出，文件变化也不再触发其他厂商的更新。建议用 `try_from_secs_f64` 和 `SystemTime::checked_add`，在单条记录范围内回退到其他时间并留下诊断。

**09｜中｜Hermes 带图片的消息会丢掉随图输入的文字**  
`src/sources/hermes.rs:125`、`src/sources/hermes.rs:178`、`src/sources/hermes.rs:197`、`src/sources/hermes.rs:337`。以文字加图片开一条会话。Hermes 给结构化内容加上 NUL 和 `json:` 前缀；适配器按普通文本取列，只对以 `[` 开头的字符串解 JSON。用相同 sqlite3 参数读取脱敏的带前缀内容，直接取列和标题用的 `substr` 都返回空字符串。计数仍可能显示一条，但首句标题、正文和搜索都缺那段文字。建议以保留字节的方式识别厂商前缀，提取文字块后再截短。[Hermes 编码实现](https://github.com/NousResearch/hermes-agent/blob/0f602c5f6f18615632535251d62a2db74ce93b69/persistence/sqlite/conversation/_store/messages.py#L57-L84)

**10｜中｜Hermes 压缩上下文后，原本仍可见的历史被会话台过滤**  
`src/sources/hermes.rs:84`、`src/sources/hermes.rs:111`、`src/sources/hermes.rs:195`。让长对话触发 Hermes 自身的压缩，再打开整段或搜索压缩前的用户原话。上游把这些行记作 `active=0, compacted=1`，自己的历史界面仍按显示顺序取回；会话台统一附加 `and active = 1`。压缩前的原话可能消失，条数随之减少。建议按上游可见性、显示顺序和去重规则还原历史，并对旧库按可用列降级。[压缩写入](https://github.com/NousResearch/hermes-agent/blob/0f602c5f6f18615632535251d62a2db74ce93b69/persistence/sqlite/conversation/_store/messages_sql.py#L82) · [历史显示查询](https://github.com/NousResearch/hermes-agent/blob/0f602c5f6f18615632535251d62a2db74ce93b69/persistence/sqlite/conversation/_store/messages.py#L1288-L1309)

**11｜中｜Hermes 已改名或已脱敏的内容可长期留在列表或搜索结果里**  
`src/sources/hermes.rs:37`、`src/index/store.rs:170`、`src/index/mod.rs:477`。先建索引，再在 Hermes 中只改标题，或原地改写消息文本。库源的会话路径为空，内容键只剩解析版本、最后活动时间、发言数。三者不变时，刷新连列表元数据也跳过。上游改标题只更新标题；原地改正文有专用 `transcript_revision`。建议单独比较列表元数据，支持该列时把正文修订号带入全文索引版本。旧词应从搜索结果中移除。[Hermes 改标题](https://github.com/NousResearch/hermes-agent/blob/0f602c5f6f18615632535251d62a2db74ce93b69/persistence/sqlite/conversation/_store/titles.py#L115) · [修订号触发器](https://github.com/NousResearch/hermes-agent/blob/0f602c5f6f18615632535251d62a2db74ce93b69/persistence/sqlite/_schema_ddl.py#L469-L476)

**12｜中｜OpenCode 一条坏 JSON 会冻结整家的列表**  
`src/sources/opencode.rs:79`、`src/sources/opencode.rs:373`、`src/sources/opencode.rs:386`。在脱敏库中保留正常会话，只让一条消息的 `data` 成为截断的 JSON。列表 SQL 对整库直接做 `json_extract`，实际返回 `malformed JSON`；本次扫描整家失败。首扫呈现空列表，已有缓存则停留在旧状态。建议按行用 `json_valid` 守护提取，保留正常会话，并汇总被跳过的行数。

**13｜中｜Kimi 和 OpenCode 1.x 撤销过的轮次仍出现在会话台**  
`src/sources/kimi.rs:79`、`src/sources/kimi.rs:91`、`src/sources/kimi.rs:311`、`src/sources/opencode.rs:143`、`src/sources/opencode.rs:370`。先发两轮，再在厂商界面撤销最后一轮。Kimi 适配器只累加 append 事件，忽略 `context.undo`；OpenCode 1.x 保留消息行，用 `session.revert.messageID` 确定应隐藏的后半段，适配器没有读取这一列。因此被撤销的发言仍计数、显示并进入搜索。建议 Kimi 重放撤销并使受影响的增量缓存失效；OpenCode 读取当前回退位置，使列表、预览和全文共用可见范围。[Kimi 撤销语义](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/reference/server-api.md#post-apiv1sessionssession_idundo) · [OpenCode 1.19.6 回退显示](https://github.com/anomalyco/opencode/blob/v1.19.6/packages/tui/src/routes/session/index.tsx)

**14｜中｜Kimi 大会话的唯一用户发言在中间时，整条会话不入列表**  
`src/sources/kimi.rs:218`、`src/sources/kimi.rs:239`。脱敏样例有有效标题，开头一条约 70 KB 的注入记录，中间一条真实提问，结尾约 200 KiB 助手输出。首尾窗口均未采到用户句，`scan()` 返回零条且无诊断。后台精确计数只处理已经入索引的会话，无法补救。建议在非整读且窗口计数为零时，按需流式查找第一条真实发言，再决定是否排除。

**15｜低｜Kimi 的两个文件只剩一个时，索引可永久保留失效会话**

**16｜中｜Qwen 遇到超长工具结果，精确计数反而丢掉前面的有效发言**

**17｜中｜Gemini 仅统计条数，也会在内存里保留整段会话正文**  
`src/sources/gemini.rs:94`、`src/sources/gemini.rs:369`、`src/sources/gemini.rs:582`、`src/index/mod.rs:539`。一条用户提问加 480 条约 120 KB 的助手记录，共约 55 MiB。临时程序计数结果为 1，进程峰值内存约 70 MiB，同一程序空载约 7 MiB。`body=false` 仅省略工具，仍为每条消息保存 `content`；后台最多同时处理八条会话。建议为计数保留 ID、角色、顺序、可见性等回放所需信息，及时释放助手和工具正文。[Gemini 自身的元数据回放](https://github.com/google-gemini/gemini-cli/blob/v0.70.0/packages/core/src/services/chatRecordingService.ts)

**18｜低｜Gemini 和 Qwen 的对话聊长以后，已改好的标题会退回首句**  
`src/sources/gemini.rs:269`、`src/sources/gemini.rs:285`、`src/sources/qwen.rs:217`。在首句后加约 100 KiB 助手输出，再写有效的 `$set.summary` 或 `custom_title`，接着产生约 110 KiB 输出。两个适配器实测均返回最初的提问。最后一个标题落在首尾窗口之间，精确计数也不修正标题。建议单独跟踪最后一个标题事件，重建时扫标题字段；Qwen 可同时核对厂商标题附属文件。

**19｜低｜OpenCode 连续执行工具后，预览可能一行字都没有**

## 索引、目录、终端和隐私

**20｜中｜Kimi 托管期间，处理一条后台消息就能让主线程重复打开数千个文件**  
`src/ui/runtime.rs:496`、`src/ui/runtime.rs:511`、`src/ui/runtime.rs:900`、`src/ui/runtime.rs:1182`、`src/sources/kimi.rs:290`。同项目有 2,000 条历史记录，再按 `n` 新建一条 Kimi。UI 每次收到后台消息都重建映射，先读取并解析每个候选的 `state.json`，随后才排除已知旧会话。在 1,999 条原有候选的脱敏样例中，单次刷新三次耗时约 79–83 ms。这是临时程序对该函数的测量；实际键盘延迟还取决于事件频率。建议索引时保存创建时刻，仅在列表或托管关系变化时刷新，并先排除已知旧 ID。

**21｜中｜不同厂商的环境配置会确定性地共用一个缓存目录**  
`src/core/dirs.rs:92`、`src/core/dirs.rs:96`、`src/index/mod.rs:151`、`src/ui/runtime.rs:141`。家目录用 `/h`，一次只设 `KIMI_CODE_HOME=/some/work`，另一次只设 `QWEN_HOME=/some/work`。实测均得到 `b0c6cb1a`。新增厂商只有偏离默认值的路径参与散列，路径所属厂商没有参与。两组因而共用全文库和项目标注，启动时还会先展示另一组的缓存。建议保留旧三家已有散列，对新增厂商把稳定的厂商名与路径共同编码。

**22｜中｜OpenCode 和 Qwen 的官方数据目录覆盖设置会让列表读错位置**  
`src/core/dirs.rs:26`、`src/core/vendor.rs:144`、`src/core/vendor.rs:158`、`src/sources/mod.rs:219`。设置 `OPENCODE_DB=work.db` 时，上游相对于 OpenCode 的数据目录解析，会话台相对于启动目录解析，还会把算错的绝对路径传回 CLI。只设 `XDG_DATA_HOME` 也会漏掉对应库。Qwen 若设 `QWEN_RUNTIME_DIR=/Volumes/Work/qwen`，会话在该目录的 `projects` 下，适配器仍扫 `QWEN_HOME/projects`。建议按厂商实现各自的路径优先级，索引、监听、缓存隔离和启动共用同一个解析结果。[OpenCode 1.19.6 库路径](https://github.com/anomalyco/opencode/blob/v1.19.6/packages/core/src/database/database.ts) · [OpenCode XDG 路径](https://github.com/anomalyco/opencode/blob/v1.19.6/packages/core/src/global.ts) · [Qwen 0.28.3 存储规则](https://github.com/QwenLM/qwen-code/blob/v0.28.3/packages/core/src/config/storage.ts)

**23｜中｜在独立终端里配置 cmux socket，会导致回车开错终端**

## 补审（12327d2..6971fad，同日）

审计范围为 `12327d2..6971fad` 的 `src` 和 `tests`。发现 **1 项高、2 项中、2 项低**。最重要的是，**静默会导致仍在工作的托管 CLI 被回收**。20 秒只会改变状态灯。真正结束进程还要求标签页已断开，且自最后一块 PTY 输出起已达到闲置时长，默认 30 分钟。

### 1. 高｜安静超时会把仍在工作的 CLI 当成可回收进程

`src/host/idle.rs:110`、`src/host/daemon.rs:1332`、`src/host/daemon.rs:1354`、`src/notify/tracker.rs:237`。断开标签页后，如果 CLI 还在等模型或工具，但终端持续没有输出，守护进程就会在闲置时长届满后的巡检中向它发两次 Ctrl+C，必要时再向进程组发 SIGTERM、SIGKILL。每秒一次的节流只影响界面事件，守护进程按**每一块** PTY 输出刷新回收计时。即使 CLI 明确报过 OSC 7501 `working`，代码也只把它记作一次输出。

用真实 **pi 1.6.0** 的交互界面和本地模拟模型做了对照。同一个 26 秒后才返回的请求，默认界面的最长输出间隔为 **0.084 秒**；用官方接口隐藏工作指示器后，最长间隔为 **25.974 秒**，随后正常收到答案。另测 pi 内置 Bash 运行无输出的 `sleep 26`，隐藏指示器后仍约每秒重画一次。是否误判取决于当时的界面和执行路径。[pi 工作指示器接口](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)

### 2. 中｜Hermes 一条无穷时间戳仍能冻结整家的索引

`src/sources/hermes.rs:110`、`src/sources/hermes.rs:280`、`src/sources/sqlite.rs:89`。上一轮的 `1e20` 已不会使索引线程 panic。但把一条消息时间写成 `1e999`，SQLite 会存成正无穷。本机系统 SQLite 3.54.0 的 `-json` 输出裸 `Inf`，整批数据在进入 `secs()` 前就解析失败。脱敏库实测，首次索引从 4 条变为 0 条；已有缓存保留 4 条，但后续 Hermes 会话不再更新。其他厂商继续工作。

**建议**在 SQL 导出时间字段前把不可表示值转为 `NULL`，并在 `max(timestamp)` **之前**过滤。否则即使是已能安全处理的 `1e20`，也会盖掉同一会话里正常的最新消息时间。预览和全文查询应采用同一规则。

### 3. 中｜OpenCode 的坏字符仍能冻结整家列表或整条会话的预览

`src/sources/opencode.rs:374`、`src/sources/opencode.rs:386`、`src/sources/opencode.rs:150`、`src/sources/sqlite.rs:89`。普通截断 JSON 的原始用例已通过。仍有两种实际失败：

- 首句包含孤立的 UTF-16 代理项 `\ud800`，例如 JavaScript 截在一个 emoji 中间后再序列化。SQLite 的 `json_valid` 返回 1，`json_extract` 却产生非法 UTF-8，导致整份列表无法解码。实测首次扫描从 5 条变为 0 条，已有缓存则停止更新。
- 把一个中文文本块按字节截在汉字中间，列表仍有 5 条，但受影响会话的预览和全文都报错，其他正常消息也看不到。

**建议**以能保留原始字节的方式传出这些字段，在 Rust 中逐行解码。坏字段只跳过对应消息或内容块。

### 4. 低｜窗口重画会让已答完的会话再显示 20 秒「在跑」

`src/notify/tracker.rs:176`、`src/notify/tracker.rs:237`、`src/host/daemon.rs:1173`、`src/host/daemon.rs:1354`。pi 答完并安静收灯后，只调整窗口大小就能触发。真实 PTY 中，答完约 23 秒后改变尺寸，pi 立即输出了约 3 KB 重画数据。守护进程知道刚发生 resize，却仍广播普通 `Output`。用当前状态机回放，灯从「等你回复」变回「在跑」，整整 20 秒后才恢复。
